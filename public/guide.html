Model guide

Two guarantees on the wire, a third you build yourself

This demo exists because "exactly-once delivery" does not exist at the network layer — it is at-least-once plus consumer bookkeeping. The lab replays one fixed lossy link so each policy's failure mode is visible in the ledger, not just in prose.

A model, not a network. Packet loss is pinned to two first-attempt ACKs and the dedupe store is a Set — the mechanism is real, the physics are simplified so the comparison stays legible.

Feature one

The lossy link

The scenario

12 charges, 2 dead ACKs

Twelve charge events at $49.00 each cross one link — an expected ledger of $588.00. Every message packet arrives at the consumer; the ACK packets for msg-03 and msg-07 die on the first attempt. The wire is identical in all three modes — only the policy around it changes.

Proves
The network sells exactly two guarantees: at-most-once and at-least-once. There is no third option at this layer.
Key detail
The ACK is itself a packet on the same lossy wire. Silence can't be distinguished from a dead message, a dead ACK, or an ACK still in flight — the Two Generals' Problem in one sentence.
The control

Same packets, same loss

Every replay crosses the identical link — same 12 events, same 2 dropped ACKs. Whatever differs in the outcome came from the sender's retry loop or the consumer's bookkeeping, never from the wire.

Proves
Differences in the ledger are caused by policy, not by luck — the comparison is controlled.
Key detail
Retries always get their ACK in this lab: only the first attempt is lossy, so a retry budget of three is never exhausted.

Feature two

The three delivery policies

At-most-once

The failure you never hear about

Fire and forget: transmit, don't wait, don't retry. The lab reports 10 confirmed, 2 unaccounted, 0 duplicates — and the ledger happens to total $588 anyway. Nobody can prove it: those two unaccounted messages are indistinguishable from loss, and resending might create the very duplicate this mode exists to prevent.

Proves
Fire-and-forget fails silently — no error, no alert, no gap in a log, because the component responsible for noticing is the ACK, and the ACK is what died.
Key detail
Fine for heartbeats and metrics where a lost sample costs nothing. Not fine for anything you'd refund over.
At-least-once

The failure you hear about twice

Retry until acked: no ACK, send again. The lab shows 14 arrivals for 12 unique events — charge-evt-03 and charge-evt-07 processed twice by a naive consumer, for a ledger of $686 against the expected $588.

Proves
Every retry converts "maybe lost" into "definitely duplicated." The message wasn't lost — the ACK was, and the retry did its job perfectly.
Key detail
You didn't remove the failure mode; you moved it downstream and handed it your customer's credit card.
Dedupe

Exactly-once as bookkeeping

Same wire, same retries — but the consumer stamps each event with an idempotency key (charge-evt-03, derived from the business identity, not a per-send UUID) and refuses any arrival whose key it has already processed. Result: 14 arrivals, 2 rejected, 12 charged exactly once — a clean $588.

Proves
"Exactly-once" is at-least-once plus a dedupe store: duplicates still happen on the network, they just die at the consumer's door.
Key detail
Real systems commit the key and the effect in the same transaction — a Redis SET NX EX, a Postgres unique constraint with ON CONFLICT DO NOTHING — so a crash can't reopen the window.

Feature three

Reading the replay

Stats + verdict

The scoreboard

Five counters summarize the run — transmissions, arrivals, the per-mode middle pair (unaccounted vs duplicates vs rejections), and the ledger total, which turns red the moment it exceeds $588. The verdict line restates each policy's trade in one sentence.

Proves
The same wire produces three different ledgers — the numbers, not the rhetoric, show who pays.
Key detail
Under at-least-once the "over" amount is exactly $98 — two $49 charges the article calls out by name.
Per-message view

Every attempt accounted for

Each card lists the event's transport id, its idempotency key, every transmission attempt with its ACK fate, and the consumer's ruling — charged, charged AGAIN, or rejected by key. Double-charged cards get a red border; unaccounted ones go dashed.

Proves
You can point at the exact message where each policy's failure mode lives.
Key detail
In dedupe mode the replay is still on the wire — the second arrival is marked "rejected by key," not erased.
Ledger + trace

The money and the mechanism

The ledger totals what a card statement would show; the interleaved trace shows wire events and consumer decisions line by line, so the causal chain — lost ACK → retry → second arrival → second charge or rejection — is never hidden.

Proves
Exactly-once emerges from the consumer's bookkeeping, never from the wire.
Key detail
The dedupe store keeps 12 keys — one per unique event — mirroring the TTL'd keyspace a real store maintains for the redelivery horizon.

Run locally

Inspect the evidence

npm test        # link semantics, all three policies, HTTP endpoints
npm run check   # test
npm start       # serve the lab on :3000

The API is inspectable directly: GET /api/scenario returns the wire, and GET /api/run?mode=at-most-once|at-least-once|dedupe returns the full trace, ledger, and summary for a replay.

Limits

What this demo does not claim

  • A deterministic in-memory model of the delivery problem — packet loss is fixed at two first-attempt ACKs; there is no clock, no timeout jitter, and no broker.
  • The dedupe store is a Set, not Redis or Postgres — real stores need a TTL covering every redelivery path (consumer lag, DLQ replay, rollback deploys) and a chosen failure policy for when the store itself is down.
  • "Exactly-once" here means effectively-once processing inside the lab — a broker's exactly-once guarantee ends at its own system boundary, always before your database.
  • Amounts are fixtures, not traffic: 12 charges of $49 because that's the scenario the article argues from.
